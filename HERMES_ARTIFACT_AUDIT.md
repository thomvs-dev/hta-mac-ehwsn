# HERMES artifact compatibility audit

HERMES contains useful diagnostic code and raw analytical trials, but it does
not contain the two artifacts needed to pass HTA-MAC Phase 0.

## Accepted evidence

- The bundled `stage1_params.mat` is byte-identical in content to the available
  solar Stage 1 export and confirms the eight-state solar parameters.
- HERMES uses the same four thermal emission defaults already frozen in
  `core/hmm/thermal_auxiliary_params.npz`.
- HERMES raw JSON files demonstrate a useful reporting format with paired seeds,
  median, IQR, and per-trial records.

## Rejected as Phase 0 substitutes

- `heart_fixed` is explicitly documented as a local analytical comparator, not
  the locked neural HEART-CH checkpoint or Table V implementation.
- The HERMES thermal chain is generated from a persistence constant; its own
  documentation says thermal-state sweeps are interpolation/plumbing tests that
  require refitting to real training traces.
- The available learned checkpoint is `W=20`, `F=33`,
  `ENVIRONMENT_KIND=realistic`, and `CH_SELECTION_MODE=quorum_cover`. It is not
  the inherited `W=10`, `F=31`, fixed-Top-K HEART-CH policy.
- The learned-policy evaluation explicitly records `hermes_included=false` and
  reports five-trial median FND 403; it cannot validate the analytical HERMES
  results or the locked HEART-CH Table V value.
- Standalone HERMES uses a 200 m maximum power range and reflective boundary
  mobility, which do not match the inherited 50 m transmission range and random
  waypoint model.

The machine-readable evidence is generated by
`validation/audit_hermes_artifacts.py` and stored in
`outputs/logs/hermes_artifact_audit.json`.
